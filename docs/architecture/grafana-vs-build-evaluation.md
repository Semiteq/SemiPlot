# Final report: where to build the trend "pen canvas" (SemiPlot). Source — PostgreSQL

## 1. Summary and primary recommendation

**Context.** The functional reference is MasterSCADA's "MasterTrend". SemiPlot's core value is not "a chart in general", but the combination of three things that almost nothing else offers: an individual axis per pen when N>2 pens (AY-2), independent per-pen Y-layer resize (PN-2), and T1/T2 measurement cursors with Δt/Δy (CU-3). Plus the hard requirement DA-1: history and realtime always come from PostgreSQL, and with your invariants (M4 decimation DA-5, NaN anchors, X monotonicity at the seam DA-7, latest-wins DA-9).

**What the research showed (objectively, without fixating on Grafana).**
- **Grafana stock is insurmountable on three MUST blockers:** AY-2 (the axis is bound to the unit, physically only 2 sides, the override is ignored when units are equal — issues #37489/#32165), consequently PN-2, and CU-3 is entirely absent. Grafana's deployment simplicity does not compensate for this — three direct user requirements cannot be met in principle.
- **Grafana-ECharts (Volkov Labs):** all MUSTs are technically achievable, but the "one stateless function → options" model resists stateful interactivity. CU-3, manual limit entry, the active pen, and window clamps require pushing state outside (Grafana variables / `window`), and the "smart provider" (DA-3/5/7/9) is delegated to Grafana+SQL and is weakly under your control. This turns into a JS application on top of ECharts inside a panel.
- **Grafana custom plugin:** 9–14 person-weeks for the MUSTs alone, coupling to unstable internal `@grafana/ui` exports (uPlot wrappers break between versions), plus the paradigm conflict of "your own time window versus the dashboard's global time range". Grafana gives you data and canvas rendering for free, but **nothing of the MasterTrend specifics**.
- **Non-Grafana, finished products:** the full combination (AY-2 + PN-2 + CU-3 + samples from PostgreSQL) exists in no open-source product. CU-3 appears only in heavy proprietary Trend Clients (AVEVA). The closest OSS options are ThingsBoard (multi-axis / manual scales / tooltip present, but no CU-3 and no log axis, PN-2/AY-2 questionable) and binjr (mature navigation / multi-axis, but no realtime, no CU-3, no SQL adapter).
- **Non-Grafana, libraries:** the best foundation is **uPlot** (MIT): the "scale per pen + manual range" model is a direct match for AY-1/AY-2/AY-3, live values in the legend (CU-1/CU-2), log axis, stepped, gaps on null. T1/T2 and the minimap are your code, but without resistance from the library. Your spec already mentions ScottPlot/Avalonia — that is, **the renderer is already chosen and the Core logic is already yours**.

**Primary recommendation.**
**Continue the in-house SemiPlot on the current stack (ScottPlot + Avalonia + your renderer-agnostic Core + the PostgreSQL provider). Grafana in all three corners fails to deliver the MasterTrend core and imposes a permanent tax (unstable API, time-model conflict, delegation of the data MUSTs). No off-the-shelf OSS analog for the full combination exists — SemiPlot fills a real niche.**

The only condition under which the decision should be revisited: if integration into the Grafana ecosystem (single auth, dashboards, a zoo of datasources) becomes a **mandatory** business requirement — then Grafana-ECharts is the least painful of the Grafana paths. But that does not change the fact that you still write the core (CU-3, AY-2, the provider) yourself.

## 3. Top 3 realistic paths

### Path A (recommended) — finish the in-house SemiPlot
**Content.** Stay on ScottPlot+Avalonia+Core+PostgreSQL provider. Close the known spec gaps rather than rebuild from scratch.
- **Effort:** estimated relative to the current state — closing the identified gaps:
  - AY-2 (runtime override of `AxisKey`, catalog not in a single group) — small;
  - DA-7 (X monotonicity in `AppendRealtime/FoldRealtime`) — small, but high priority (correctness risk);
  - UI wiring of what is already modeled in Core: AY-5 (autoscale-to-window), AY-6 (log axis in `ChartAxisBinder`), DA-4 (manual layer selector), CU-6 (readout at live-edge), DA-6 (column stability).
  - Benchmark: **finishing the MUSTs + the listed SHOULD gaps — on the order of a few weeks**, since the core already works.
- **Risks:** low and under your control. The main one is ScottPlot's log-axis render specifics (a real log axis type is needed, not a linear `SetLimitsY` clamp). No external coupling to someone else's unstable API.
- **Plus:** all data MUSTs (DA-5/6/7/9) remain yours and verifiable by unit tests.

### Path B (fallback, if Grafana becomes mandatory) — Grafana-ECharts panel (Volkov Labs)
**Content.** Implement the canvas as a Charts function on top of a live ECharts instance; queries/aggregation in a Grafana PostgreSQL datasource + SQL.
- **Effort:** medium. The declarative parts (axes, the dataZoom-slider minimap, legend toggle, tooltip, manual limits) are quick. Expensive: **CU-3** (T1/T2 + delta + interpolation + a no-pan mode), pushing all stateful state outside, manual layout of N axes (`offset`/`grid`), wiring DA-3/5/7/9 to the datasource + variables + datazoom handlers.
- **Risks:** stateless function vs stateful application (loses state on every re-render — needs `.off()` before `.on()` and external storage); control over data loading leaves your code and moves into the "time range + SQL + variables" combination; your M4/NaN invariants reproduce poorly in someone else's pipeline.
- **When to take it:** only if Grafana integration is a firm requirement. It provides Grafana deployment/SSO/dashboards, but you still write the core yourself.

### Path C (compromise on an external base outside Grafana) — ThingsBoard CE as a base + extend
**Content.** Take the ThingsBoard Time Series Chart (Apache-2.0, PostgreSQL out of the box): multi-axis, manual scales, zoom, hover readout — out of the box. Add CU-3, AY-6 (log axis), validate PN-2 and AY-2 on a test bench as the canonical case.
- **Effort:** medium-high, plus a mandatory bench validation (PN-2/AY-2 not confirmed by the documentation).
- **Risks:** the licensing fork (Trendz/PE are paid; stay within CE); it is a "dashboard widget", not a SCADA pen canvas — the "active pen" model and layer resize are questionable; dependency on a third-party product and its release cycle.
- **When to take it:** if you need a ready device/telemetry platform around the trend, not just a chart.

**Rejected as not cost-effective under this spec:** Grafana stock (3 MUST blockers), Grafana custom plugin (9–14 weeks + unstable internal API + time-model conflict), dygraphs (≤2 axes), Superset/Metabase/Redash (BI, no operator cursors), Grafana Scenes (bound to Grafana → outside the "no-Grafana" track), PlotJuggler (no PostgreSQL and no CU-3, a C++/Qt fork outside your stack).

## 4. What to do next (step by step)

1. **Lock the decision:** continue the in-house SemiPlot (Path A). Keep the Grafana options as a documented fallback in case Grafana integration becomes a mandatory business requirement.
2. **Close the correctness risk first — DA-7** (X monotonicity at the history↔realtime seam in `TrendPenState.AppendRealtime/FoldRealtime`: drop/clamp X ≤ the last). Cover with a unit test "a realtime point with X ≤ the end of history does not make the line go backward".
3. **Close the multi-axis core — AY-2:** make `PenScaleSettings.AxisKey` overridable at runtime and remove the grouping of the "gas lines" catalog into a single group. Test: N pens with unique `AxisKey` → N independent axes.
4. **Wire to the UI what is already modeled in Core (eliminate the "model exists — UI missing" gap):**
   - AY-6 log axis — a real log axis type in `ChartAxisBinder`, not a linear clamp; add a toggle.
   - AY-5 autoscale-to-window — a command/toggle, recompute on window change.
   - DA-4 manual layer selector — an interactive combobox + lock instead of read-only text.
   - CU-6 — recompute the readout under a stationary cursor at live-edge.
   - DA-6 — distribute columns across segments so as not to overflow `targetColumnCount`.
5. **Run the MUST acceptance by the spec's rubrics:** Core/test (navigation round-trip without drift, decimator min/max + NaN anchors, DeltaCursorModel, latest-wins), DB (real PostgreSQL: history fills the canvas, extent from the DB, connection loss → failed `Result` without a UI crash), UI (synchronous pen shift, band when Min≠Max, T1/T2 delta).
6. **Calibrate UX against references** (as reference only, not for embedding): the pens/axes model — **Ignition Easy Chart**; specifically T1/T2 + values in cursors — **AVEVA Trend Client**.
7. **Borrow the DB schema and the "aggregates on the PostgreSQL side" pattern (DA-2)** from `json-scada` and `awcullen/historian`; the multi-axis/time-range UI mechanics — from `binjr`.
